# Create Rules

プロジェクトのコード変更やコードベースを分析し、プロジェクト固有のベストプラクティスや規約を `.claude/rules/` ファイルとして抽出・保存する (pi では claude-rules extension がこれらのルールを自動で読み込む)。

## 作業開始前の準備

**必須:** 作業開始前に `todo({ action: "list" })` で残存タスクを確認し、存在する場合は `todo({ action: "clear" })` で全て削除する。その後、`todo` tool で以下のステップをタスクとして登録する:

```
todo({ action: "add", text: "分析対象の特定 (PR URL、staged/unstaged diff、または question でスコープを決定)" })
todo({ action: "add", text: "既存ルールの確認 (.claude/rules/ の既存ファイルを把握)" })
todo({ action: "add", text: "コード分析と規約抽出 (プロジェクト固有の規約を抽出)" })
todo({ action: "add", text: "ルールファイルの設計 (paths スコープとファイル分割を設計)" })
todo({ action: "add", text: "ルールファイルの作成・更新" })
todo({ action: "add", text: "既存ルールとの統合検討 (分割・統合・更新の必要性を検討)" })
todo({ action: "add", text: "結果の確認 (作成・更新したルールファイルの最終確認)" })
```

各ステップの完了時に `todo({ action: "toggle", id: <id> })` で完了済みに更新する。

## 処理フロー

### Step 1: 分析対象の特定

引数として GitHub PR URL が渡された場合:

- PR URL から owner/repo と PR 番号を抽出
- `gh pr diff <PR_NUMBER> --repo <OWNER/REPO>` で変更差分を取得
- `gh pr view <PR_NUMBER> --repo <OWNER/REPO>` で PR の概要を把握

引数が渡されていない場合、デフォルトで staged/unstaged diff を分析対象とする:

- `git diff` と `git diff --cached` で現在の作業中の変更差分を取得
- diff が空の場合は `question` tool で分析対象を尋ねる:
  - **プロジェクト全体**: コードベース全体から規約を分析
  - **ブランチ差分**: 現在のブランチと親ブランチ (main/master) の diff

### Step 2: 既存ルールの確認

`.claude/rules/` ディレクトリを確認し、既存のルールファイルを把握する:

- `find` tool で `.claude/rules/**/*.md` を検索
- 既存ファイルがある場合は全て読み込み、内容を把握
- 重複回避と分割・統合の判断材料として保持する

### Step 3: コード分析と規約抽出

分析対象のコードから、プロジェクト固有のベストプラクティスや規約を抽出する。

#### 抽出対象 (プロジェクト固有の内容のみ)

- プロジェクト固有のディレクトリ構造・ファイル配置規約
- カスタムの命名規則 (変数、関数、ファイル、ディレクトリ)
- プロジェクト固有のエラーハンドリングパターン
- 特定の内部 API やユーティリティの使用パターン
- カスタムの型定義・インターフェース設計パターン
- テストの書き方に関するプロジェクト固有の慣例
- 特定のライブラリのプロジェクト内での使い方 (ラッパーパターン等)
- コード生成やボイラープレートの規約
- 環境固有の設定パターン
- ドメインロジックの表現パターン

#### 除外対象 (agent にとって冗長な一般的知識)

- 言語の公式スタイルガイド (PEP8, Google Style Guide, Effective Go 等)
- フレームワークの標準的な使い方 (React の基本パターン、Express のミドルウェア等)
- 一般的なデザインパターン (Singleton, Observer, Factory 等)
- 言語の基本構文やイディオム
- 標準的な Linter/Formatter の推奨ルール (ESLint recommended, Prettier defaults 等)
- 一般的なセキュリティプラクティス (OWASP Top 10 等)
- Git の標準的なワークフロー
- 標準的なテストのベストプラクティス (AAA パターン等)

#### 判断基準

規約を抽出する際に、以下の問いで判断する:

1. **このプロジェクト独自か?** - 他のプロジェクトでも同じルールが適用されるなら除外
2. **agent が既知か?** - 言語・フレームワークの公式ドキュメントに記載されている内容なら除外
3. **具体的か?** - 「良いコードを書く」のような抽象的なルールは除外、「エラーは AppError クラスでラップする」のような具体的なルールは抽出
4. **摩擦を解決するか?** - このルールがないと agent が間違った実装をしそうな内容を優先

### Step 4: ルールファイルの設計

#### paths によるスコープ設定

コンテキスト節約のため、可能な限り `paths` のスコープを小さく設定する:

- ルールが特定のディレクトリにのみ適用される場合は、そのディレクトリに限定
- 複数のディレクトリに適用される場合は、glob のブレース展開を活用
- プロジェクト全体に適用されるルールのみ `paths` を省略

`paths` の記法と例は `references/rules-format.md` を参照。

#### ファイル分割の方針

- **1 ファイル 1 トピック**: 異なるドメイン・レイヤーのルールは別ファイル
- **ファイル名**: ルールの内容を表すケバブケース (例: `api-error-handling.md`, `component-structure.md`)
- **サブディレクトリ**: 関連するルールが多い場合はサブディレクトリで整理 (例: `frontend/`, `backend/`)

### Step 5: ルールファイルの作成・更新

ルールファイルを作成する際のフォーマット:

```markdown
---
paths:
  - 'src/api/**/*.ts'
---

# [ルールのタイトル]

[具体的なルールの記述]
```

記述スタイル:

- 簡潔で具体的な箇条書きを優先
- コード例は最小限 (必要な場合のみ)
- 「なぜ」よりも「何を」にフォーカス
- agent にとって冗長な説明は省略

### Step 6: 既存ルールとの統合検討

既存の `.claude/rules/` ファイルがある場合、以下を検討する:

#### 統合 (マージ)

- 同じトピック・同じ paths スコープのルールが複数ファイルに分散している場合
- ファイル数が多すぎて管理が煩雑な場合

#### 分割

- 1 ファイルに異なる paths スコープのルールが混在している場合
- 1 ファイルのルールが肥大化している場合 (目安: 50 行超)

#### 更新

- 既存ルールと矛盾する新規ルールがある場合は、既存ルールを更新
- 重複するルールは統合し、より具体的な記述に改善

統合・分割・更新を行う場合は、変更内容をユーザーに提示して確認を取る。

### Step 7: 結果の確認

作成・更新したルールファイルの一覧を表示し、内容の最終確認をユーザーに求める。
