# フィードバック検証・反映ワークフロー

引数で受け取ったフィードバックやレビュー内容の妥当性を検証し、現在のコンテキストに照らして「修正すべき指摘」だけを反映する。妥当な指摘でもスコープ外・方針と異なる場合は修正せず、理由付きで報告する。

## 重要な原則

1. **妥当性を必ず検証** - 指摘を鵜呑みにせず、実際のコードと差分を確認し、事実誤認・論理矛盾・既対応がないか吟味する
2. **現在のコンテキストを基準にする** - 修正の要否はセッションの方針とブランチ差分に照らして判断する
3. **スコープ外・方針違いは修正しない** - 妥当な指摘でも今回の変更範囲外、または確立済みの方針と異なるなら反映せず報告のみ行う
4. **判断が不明瞭なら確認** - 妥当性やスコープの判断がつかない場合は推測せず question / questionnaire tool で確認する
5. **修正は即実施し、結果を報告** - 修正対象と判定した指摘はそのまま反映し、判定結果と対応内容をまとめて報告する

## 現在のコンテキストの定義

「現在のコンテキスト」は次の 2 要素で構成する:

1. **セッション中のコンテキスト情報** - これまでの会話で確立した目的・設計判断・方針・制約・既知の検討事項
2. **差分** - 現在のブランチに応じて取得方法を切り替える (デフォルトブランチは `origin/HEAD` から検出し、`main` は決め打ちしない):
   - **デフォルトブランチ以外**: 分岐元 (merge-base) から現在のブランチまでの差分
   - **デフォルトブランチ**: staged + unstaged の差分

## 作業開始前の準備

指摘が 3 件以上、または検証に複数ファイルの確認が必要な場合は todo tool でステップを管理する。1〜2 件の単純な検証ならタスク登録なしで直接進める。

タスク登録する場合は、まず `todo({ action: "list" })` で残存タスクを確認し、存在する場合は `todo({ action: "clear" })` で全て削除する。

```
todo({ action: "add", text: "フィードバックの取得と分割 (引数 (なければ確認) を個別の指摘単位に分割)" })
todo({ action: "add", text: "現在のコンテキストの収集 (セッション方針とブランチ差分を取得)" })
todo({ action: "add", text: "各指摘の検証と判定 (妥当性・スコープ・方針整合性を判定し分類)" })
todo({ action: "add", text: "修正の実施 (修正対象と判定した指摘を反映)" })
todo({ action: "add", text: "完了報告 (判定結果と対応内容をまとめて報告)" })
```

各ステップの完了時に `todo({ action: "toggle", id: <id> })` で完了にする。

## 実行手順

### 1. フィードバックの取得と分割

引数があればそれを検証対象とする。複数の指摘が含まれる場合は、独立して判定できる**個別の指摘単位に分割**する (番号付きリスト、箇条書き、段落、「と」「、」区切り等を認識)。

**引数がない場合は必ず question tool で検証対象のフィードバック/レビュー内容を尋ねてから進める。** 直近の会話やコードから推測して勝手に対象を決めない。

```
question({
  question: "検証・反映するフィードバックやレビュー内容を入力してください。",
  options: [
    { label: "入力する", description: "「Type something...」からフィードバック内容を記載します" }
  ]
})
```

### 2. 現在のコンテキストの収集

#### 2-1. セッション方針の把握

これまでの会話から、今回の作業の**目的・スコープ・確立済みの設計判断・意図的な選択**を整理する。これが後段の「方針整合性」判定の基準になる。

#### 2-2. ブランチ差分の取得

現在のブランチを判定し、差分を取得する:

```bash
# Git リポジトリ外なら差分は取得せず、セッションのコンテキストのみで検証を続ける
if ! git rev-parse --is-inside-work-tree >/dev/null 2>&1; then
  echo "Git リポジトリ外: ブランチ差分なし (セッションのコンテキストで検証)"
else
  current=$(git rev-parse --abbrev-ref HEAD)

  # デフォルトブランチを origin/HEAD から検出 (master/trunk 等にも対応。main は決め打ちしない)
  default=$(git symbolic-ref --quiet --short refs/remotes/origin/HEAD 2>/dev/null | sed 's@^origin/@@')

  if [ "$current" = "$default" ]; then
    # デフォルトブランチ: staged + unstaged の差分
    git diff HEAD
  else
    # デフォルトブランチ以外: 分岐元 (merge-base) から作業ツリーまでの差分 (コミット済み + 未コミット)
    # ローカル $default → origin/$default の順で merge-base を解決
    base=""
    [ -n "$default" ] && base=$(git merge-base "$default" HEAD 2>/dev/null || git merge-base "origin/$default" HEAD 2>/dev/null)
    if [ -n "$base" ]; then
      git diff "$base"
    else
      # 分岐元を特定できない場合、git diff HEAD はコミット済みのブランチ変更を
      # 取りこぼし空差分になり得るため使わず、ブランチ差分なしとしてセッションのコンテキストで検証する
      echo "分岐元を特定できないためブランチ差分なし (セッションのコンテキストで検証)"
    fi
  fi
fi
```

- `git diff "$base"` は分岐点から作業ツリーまでの全変更 (コミット済み + 未コミット) を含む。指摘がブランチでの作業全体に対するものか、未コミット分のみかを区別したい場合は `git diff "$base" HEAD` (コミット済みのみ) も併用する。
- 差分が空の場合でも、セッションのコンテキストを基準に検証を続ける。

### 3. 各指摘の検証と判定

各指摘について、関連ファイルを read tool で読み込んだ上で次の 3 観点を順に判定する。**判定の詳細な基準は `references/evaluation-criteria.md` を参照。**

1. **妥当性 (Validity)** - 指摘は技術的に正しいか。事実誤認・論理矛盾はないか。既に対応済みでないか
2. **スコープ (Scope)** - 今回のコンテキスト (差分とセッションの目的) が扱う範囲内か
3. **方針整合性 (Alignment)** - セッションで確立した方針・意図的な選択・プロジェクト規約と一致するか

#### ファクトチェック (妥当性検証で必須)

技術的な主張を含む指摘は鵜呑みにせず、**最新のドキュメントと、プロジェクトが実際に使用している言語・ツールの API バージョンに沿った情報**で裏付けを取る。特に次のケースでは必ず実施する:

- 言語仕様・ランタイムの挙動、フレームワーク・ライブラリの API や推奨パターン
- セキュリティ・パフォーマンスに関する主張
- 「〜すべき」「〜は非推奨」など規範的・断定的な主張

手順:

1. **使用バージョンを特定する** - 指摘対象の言語・ツールについて、プロジェクトが実際に使うバージョンを確認する。依存マニフェストやロックファイル、ランタイム指定ファイル (例: `package.json` / `bun.lock`、`go.mod`、`Cargo.toml`、`pyproject.toml` / `requirements.txt`、`.tool-versions` / `.nvmrc`) を read tool で読む
2. **そのバージョンの情報で照合する** - 指摘が前提とする API・挙動・推奨が、特定したバージョンに実在し有効か確認する。指摘が別バージョン (新しすぎる/古すぎる) や非推奨化前の前提に基づいていないか検証する
3. **最新動向も確認する** - 非推奨・破壊的変更・新 API の有無を最新ドキュメントで確認する。最新安定バージョンの調査が必要な場合は `subagent` tool で `latest-version` agent に委譲できる

**ソースの優先順位:**

| 優先度 | ソース             | 用途                                                   |
| ------ | ------------------ | ------------------------------------------------------ |
| 1      | LSP                | コードベース内の定義・参照・型情報の確認               |
| 2      | deepwiki MCP       | OSS リポジトリの Wiki・ドキュメント (mcp tool 経由)    |
| 3      | context7 MCP       | ライブラリの公式ドキュメントとコード例 (mcp tool 経由) |
| 4      | ax (bash 経由)     | 公式サイト・GitHub・リリースノート等の直接取得         |

**例外 (上記より優先):**

- terraform は terraform MCP が最優先 (mcp tool 経由)
- Google Cloud は google-developer-knowledge MCP が最優先 (mcp tool 経由)

ファクトチェックの結果は妥当性の根拠とする。指摘が古い情報や別バージョンの前提に基づき成立しない場合は「妥当性に欠ける」と分類し、確認したソースを報告に添える。

判定結果で各指摘を分類する:

| 妥当性 | スコープ | 方針 | 分類                      |
| ------ | -------- | ---- | ------------------------- |
| ◯      | 内       | 一致 | **修正対象**              |
| ◯      | 外       | -    | 報告のみ (スコープ外)     |
| ◯      | 内       | 違い | 報告のみ (方針と異なる)   |
| ✕      | -        | -    | 報告のみ (妥当性に欠ける) |
| 不明   | -        | -    | 確認 (Step 4 へ)          |

### 4. 不明瞭な場合の確認

妥当性・スコープ・方針のいずれかが判断できない指摘は、推測で処理せず questionnaire tool でまとめて確認する。指摘ごとに個別質問するのではなく、判断がつかない箇所を 1 回で確認する (1 件のみなら question tool でよい)。

### 5. 修正の実施

「修正対象」と分類した指摘を edit / write tool で即座に反映する。

- 既存コードのスタイル・規約・命名に合わせる
- 1 つの指摘に複数箇所の変更が必要な場合は漏れなく反映する
- 修正によって新たな不整合 (型エラー、未使用、参照切れ等) が生じないか確認する
- プロジェクトのタスクランナー (`bun fmt` 等) があれば整形・検証を実行する

### 6. 完了報告

判定結果と対応内容をまとめて報告する。**報告フォーマットは `references/evaluation-criteria.md` の「報告フォーマット」を参照。** 最低限、次を含める:

- **修正を実施した指摘**: 指摘内容 / 対応内容 / 変更ファイル
- **修正を見送った指摘**: 指摘内容 / 判定 (スコープ外・方針と異なる・妥当性に欠ける) / 理由

## エラーハンドリング

### Git リポジトリ外で実行した場合

ブランチ差分は取得できない旨を伝え、セッションのコンテキスト情報のみを基準に検証を続ける。差分による裏付けができない判定はその旨を報告に明記する。

### 差分が空の場合

ブランチ差分が取得できなくても、セッションで確立した方針を基準に妥当性・方針整合性を判定する。スコープ判定は差分がない前提で慎重に行う。

### 指摘がすべて修正不要だった場合

修正は行わず、各指摘について見送り理由を明記して報告する。妥当な指摘を「スコープ外」「方針と異なる」として見送る場合は、後続で対応する余地があることも併記する。

### 関連ファイルが読み込めない場合

該当指摘の妥当性検証をスキップし、確認が必要な旨を報告に明記する。
