# 解説の執筆ガイド

pr-explain が解説本文を書く際の文体・構成・図示の指針を定める。日本語の書式ルール (スペース、句読点、括弧) は `japanese-text-style` スキルに従う。本ガイドが扱うのは「読み物としての質」である。

## 文体の原則

### 1. セクション間を滑らかに繋ぐ

各セクションを独立した箇条書きの塊にしない。前のセクションで述べたことを受けて次を始める。

**良い例:**

```
## 直感

前節で見たとおり、これまで検証は受信直後の 1 箇所に集中していた。
この PR が変えたのは、その集中を解いた点である。
```

**悪い例:**

```
## 直感

この PR の核心は検証タイミングの変更である。
```

### 2. 抽象の前に具体

概念を導入する前に、それが必要になる場面を示す。「`RetryPolicy` を導入した」ではなく、「タイムアウトのたびに手書きの `for` ループを書いていた。これを `RetryPolicy` に集約した」と書く。

### 3. 既知から未知へ

読者が既に知っているものを足場にする。新しいデータ構造を説明するときは、既存のどれに似ていて、どこが違うのかを先に述べる。

### 4. 「なぜ」を必ず書く

「〜を追加した」で止めない。「〜のため〜を追加した」まで書く。動機が diff から読み取れない場合は、PR description、Issue、レビュー議論、コミットメッセージから探す。それでも見つからなければ「description には記載がないが、コードの構造から〜と読み取れる」と推測であることを明示して書く。

### 5. 断定する

「〜と思われる」「〜の可能性がある」を多用しない。根拠がある場合は断定し、根拠がない場合は根拠がないことを明示する。曖昧なヘッジは読者の判断材料を奪う。

## 背景説明の 2 層構造

背景説明は 2 つの層に分ける。読者の前提知識が不明なため、深い層は読み飛ばせる形にする。

### 層 1: 前提となる仕組み

変更対象が属する既存システムの説明。**diff に映っていないコードの説明が中心**になる。

- 変更対象のモジュールが何を担っているか
- どこから呼ばれ、何に依存しているか
- なぜ現在の設計になっているか

冒頭に「この領域に馴染みがあれば読み飛ばしてよい」と明記する。

### 層 2: この変更の動機

変更に直結する背景。何が問題で、なぜ今それを直すのか。

- PR description / Issue に書かれた課題
- レビュー議論で明らかになった設計判断の理由
- 既存実装の限界

## 直感セクションの書き方

**このセクションが解説の核心である。**「コードがどう変わったか」ではなく「何が本質的に変わったか」を伝える。

### 構成

1. **一言要約** — 「一言でいえば〜」で始め、変更の本質を 1 文に圧縮する
2. **トイデータによる Before/After** — 具体的な値を入れた最小の例で、変更前後の挙動の違いを見せる
3. **含意** — その変化が何をもたらしたか (責務の移動、不変条件の追加、性能特性の変化など)

### トイデータの粒度

- **実在するフィールド名・型名を使う**。架空の `foo` / `bar` ではなく、そのコードベースの語彙で書く
- **3-5 行に収める**。データが大きいと本質が埋もれる
- **境界値を選ぶ**。変更の効果が最も明確に現れる入力を選ぶ (空配列、null、上限超過など)
- **Before と After を同じ入力で比較する**。入力が変わると差分が読み取れない

### 例

```markdown
## 直感

一言でいえば、検証の責務が受信層からドメイン層に移った。

`{ userId: "u1", amount: -100 }` という不正な入力で追ってみる。

| 段階         | Before                              | After                                      |
| ------------ | ----------------------------------- | ------------------------------------------ |
| ハンドラ受信 | `validate()` で `amount < 0` を弾く | 素通し                                     |
| ドメイン生成 | 到達しない                          | `Order.create()` が `InvalidAmount` を返す |
| レスポンス   | 400 (メッセージはハンドラ由来)      | 400 (メッセージはドメイン由来)             |

外から見た振る舞いは同じだが、「金額は正でなければならない」という規則の置き場所が変わった。
同じ規則をバッチ処理から呼んだときにも効くようになったのが実質的な変化である。
```

## 図示の指針

### コマンドライン出力時 (デフォルト)

- **ASCII アート図は使わない**。端末幅で崩れ、情報密度が低い
- **Mermaid 記法は使わない**。ターミナルではレンダリングされず、生のコードが表示されるだけになる
- 代わりに次を使う:
  - **Before/After 対比表** — 状態や挙動の変化
  - **番号付きの処理フロー** — 時系列・呼び出し順
  - **入出力例** — 具体的な値を含むコードブロック
  - **ネストしたリスト** — 階層構造

### `--html` 指定時

docs-html skill に渡す中間 md には、図があると有効な箇所に HTML コメントで指示を残す。

```markdown
<!-- FIGURE: データフロー図。Handler → UseCase → Repository の 3 ノード。
     Before は Handler に検証が付き、After は UseCase に移る。
     エッジには { userId: "u1", amount: -100 } を流す -->
```

指示には必ず **図の種類・登場要素・流れる例示データ** を含める。抽象的な「ここに図」だけでは委譲先が具体化できない。

### 図ファミリの再利用

1 つの解説の中で図の種類を増やしすぎない。2-3 種類を選び、繰り返し使う。有効な組合せ:

- **UI 模式図** — 画面の変更を説明する場合
- **データフロー図** — コンポーネント間の通信・データの流れ (例示データを必ず載せる)
- **状態遷移図** — 状態機械やライフサイクルの変更

## レビュー議論の織り込み方

レビューコメントを独立セクションにまとめない。該当する説明の文脈に織り込む。

**良い例:**

```
この分岐は当初 `if` の連鎖で書かれていたが、レビューで
「条件が 4 つを超えると読めない」と指摘され、テーブル引きに変わった
(plugins/git/skills/pr-explain/SKILL.md:42)。
```

**悪い例:**

```
## レビューでの議論

- レビュアー A: 条件が多すぎる
- 作者: テーブル引きに変更しました
```

未解決スレッドは「この点は未決着である」と明示する。解決済みスレッドは結論だけを織り込み、経緯は結論の理解に必要な範囲に留める。

## 品質チェック

出力前に次を自問する。

- [ ] **対応概要** を読むだけで変更の全体像が掴めるか
- [ ] **前提となる仕組み** に、diff に映っていないコードの説明が含まれているか
- [ ] **この変更の動機** から「なぜ今これをやるのか」が読み取れるか
- [ ] **直感** に具体的な値を含むトイデータがあるか
- [ ] **直感** が「コードの説明」になっていないか (本質の説明になっているか)
- [ ] **実装説明** が diff の並び順ではなく論理的な順序になっているか
- [ ] ファイルパスと行番号が具体的に参照されているか
- [ ] ASCII 図・Mermaid をコマンドライン出力に混ぜていないか
- [ ] 根拠のないヘッジ表現 (「〜と思われる」) を使っていないか
