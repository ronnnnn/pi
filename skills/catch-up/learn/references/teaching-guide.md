# 教え方の詳細ガイド

## 説明レベル (ユーザーの要求に応じて切り替える)

ユーザーは理解度に応じて以下のレベルでの説明を求めることがある。要求されたレベルに正確に合わせる。

| 要求    | 対象       | 説明の方針                                                              |
| ------- | ---------- | ----------------------------------------------------------------------- |
| `eli5`  | 5 歳児     | 専門用語を完全に排除し、身近な比喩で本質だけを伝える                    |
| `eli14` | 14 歳      | 基本的な比喩を使いつつ、仕組みの概要まで踏み込む                        |
| `elii`  | インターン | 専門用語を使い、コードや設計判断の根拠まで具体的に説明する (実務レベル) |

要求がなくても、ユーザーの言い直しから理解度を推定し、適切なレベルから始める。理解が浅い項目は `eli5` 寄りから入り、段階的にレベルを上げる。

## 現在地の把握 (restate first)

教える前に、必ずユーザー自身に理解を言い直してもらう。

- 「今わかっている範囲で、この変更を説明してみてください」
- 「なぜこの方法を選んだと思いますか？」

言い直しから誤解・抜けを特定し、そこを優先して埋める。先回りして全部説明しない。

## クイズ設計 (question tool)

理解の確認は必ずクイズで行う。説明を聞いただけでは習得とみなさない。

### 鉄則

1. **正解の位置は SSoT (String Seed of Thought) で決める**: モデルは放っておくと正解を必ず先頭 (1 番目) に置きがちで、「ランダムに置け」と指示してもこの偏りは直らない。そこで、先に乱数の種となる文字列を自分で生成し、それを機械的に変換して位置を導出する。外部の乱数生成器は不要で、思考の中で完結する。
   1. まず誤答 (distractor) だけを列挙する。
   2. **種文字列を生成する**: 半角英数字 (ASCII) のみで、英字から始まる意味のないランダムな文字列を 1 つ書き出す (例: `q7fk2m`)。全角文字や記号は混ぜない。前問と同じにしない。
   3. **種から位置を導出する**: 種文字列の最初の英字のアルファベット順位置 (a=1, b=2, …, z=26。大文字小文字は区別しない) を求め、`位置 = (アルファベット位置 mod 選択肢数) + 1` で算出する (1 始まり)。文字コードの合計より計算が単純で、桁数が小さいため算出ミスを避けられる。
   4. 算出した位置に正解を挿入し、残りを誤答で埋める。

   実施例 (選択肢 4 つ):

   ```
   種: "q7fk2m" → 最初の英字 "q" はアルファベットの 17 番目
   位置 = (17 mod 4) + 1 = 1 + 1 = 2 → 正解は 2 番目
   ```

   毎問で種を引き直すため、位置は問ごとに変わり、先頭固定の偏りも、ローテーションのような予測可能なパターンも避けられる。

   > SSoT は Sakana AI が提案した手法。LLM が苦手な「確率分布に従ったサンプリング」を、ランダム文字列を種にすることで近似する。出典: https://sakana.ai/ssot/

2. **送信まで正解を明かさない**: 質問文や選択肢の説明に正解のヒントを埋め込まない。回答送信後に正否と解説を示す。
3. **不正解は再挑戦**: 間違えた項目はチェックリストを完了にせず、理解を補強してから別の角度で再クイズする。

### 質問タイプ

- **自由記述 (open-ended)**: 「なぜ X ではなく Y を選んだのか説明してください」のように深い理解を問う。question tool は選択式が基本のため、自由記述で問う場合は通常のテキストでの問いかけとして投げ、ユーザーの回答文を評価する。
- **選択式 (multiple choice)**: question tool を使い、紛らわしい誤答 (distractor) を混ぜて理解の精度を測る。各選択肢の説明には正解を示唆しない中立的な説明を置く。

### 質問例

```
問題: この変更で導入したリトライ処理について、最も正確なものはどれ？
- 指数バックオフで最大 3 回再試行する
- 失敗したら即座に例外を投げる
- 無限にリトライする
- 1 秒間隔で固定回数リトライする
```

(上記はあくまで例。実際の正解位置は鉄則 1 の SSoT 手順で決める)

## コード・デバッガの活用

言葉だけで理解が難しい場合、実物を見せる:

- 該当コードを read で提示し、行レベルで何が起きているか追わせる
- 必要に応じてデバッガの使用を促し、ブレークポイントで変数の変化を観察させる
- `git diff` の該当箇所を一緒に読み、変更前後の差分から設計判断を理解させる

## 完了の判断

以下を全て満たしたときのみ完了とする:

- チェックリストの全項目が `- [x]`
- 各項目についてユーザーがクイズで理解を実証した
- 総合クイズ (全体俯瞰) に正答した

満たさない限りセッションを終えない。
